# Persona 6 — fourteen agentic chats

Independent first-round review, 5 October 2026. Review only; no source changes or running models.

## Goals and evidence

Persona hypothesis: I am a man managing fourteen open agentic chats. I need to scan which work needs attention, return to the right conversation, and avoid changing the shared engine while other work depends on it. Fourteen chats are fourteen contexts to manage; they do not imply fourteen inference jobs running simultaneously. I favor compact facts over explanatory paragraphs, but a global change needs an unmistakable scope label.

Observed: inspected `01-engine-light.png`, `07-models-light.png`, `09-onboarding-profile.png`, and `08-variant-comparison.png` via image viewing, plus current Tuning, Models, Setup, EngineExperience, ModelCatalog, experience, and the relevant Serving/store sections. Engine's dials and memory impact are clear, but their captions, introduction, and preview story consume substantial space. Models repeats the exact Balanced/Performance winner in two tall cards. Comparison repeats an entire expected-experience card three times. Onboarding repeats profile purpose in both the selector and the selected recommendation.

Observed: Models explicitly says “one model runs at a time”; Serving says requests take turns and exposes active/queued counts. ModelAction gates its switch confirmation on running plus waiting requests. The store's shared lifecycle guard checks streaming/running requests, not waiting counts; Tuning's restart dialog only says to wait for active requests and does not disable its confirmation based on request activity. These are UI/guard observations, not proof that the backend interrupts queued jobs. Native integration is deferred. The performance estimator omits scheduling and reasoning; memory is one configuration estimate, not fourteen-chat aggregate memory.

Relevant interaction rules: one hero per screen, density for scanning, no decorative motion during generation, navigation and per-conversation reading continuity. An orchestration dashboard, automatic scheduler, or new parallel execution promise would exceed this review.

## Friction

- The loaded-model summary, draft status, and queue facts live in different places; the user must reconstruct the scope of an action.
- “Prompt batch” plausibly reads as a parallel-jobs control to this persona. It actually concerns prompt text processed together.
- Large speed numbers lack a nearby scheduling qualifier. The current qualifier exists inside Estimate details, too far from a quick throughput decision.
- “Save for next load” is clear for resource settings, but the same save can change sampling defaults for the next request across chats.
- Repeated prose obscures actionable differences among exact model variants.

## Vote and opposition

Three must-do votes: **1** compact global state/activity, **4** consistent explicit switching gates, and **7** comparable rows with visible per-request/scheduling limits. I support reducing card prose through progressive disclosure; I would ship these before adding any new session-management features.

Oppose: (a) hiding global scope, active/queued blockers, memory fit or Demo status in the pursuit of less text; these are operational facts, not optional education. (b) a “14 parallel agents” capacity dial, per-chat model promise, aggregate ETA, or automatic queue/switch scheduler. The present host exposes one loaded model with requests taking turns, and current evidence cannot substantiate such claims.

Remaining persona hypotheses to validate later: whether a single shared activity line adequately reassures a fourteen-chat operator, and whether “tokens per pass” is sufficiently understandable. Neither is a reason to invent a concurrency model or run models during this review.
